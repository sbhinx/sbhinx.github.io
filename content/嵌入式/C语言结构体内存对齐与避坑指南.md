在嵌入式开发中，经常需要定义报文协议、寄存器映射结构体或与外设直接做 DMA 数据搬运。理解结构体的**内存对齐（Alignment）与填充（Padding）**，是写出高可靠底层代码的基本功。

> [!NOTE]
> 在前文 [[嵌入式/CAN协议快速入门|CAN 总线协议快速入门]] 中，定义通信报文结构体时，如果不注意对齐，很容易导致发送和接收双方解析出来的字段错位！

---

## 1. 为什么 CPU 需要内存对齐？

许多开发者误以为内存是一个个按单字节读取的，实际上现代处理器（如 ARM Cortex-M / RISC-V / TriCore）是以**字（Word，如 32-bit 即 4 字节）**为边界访问总线的：

* **对齐访问**：地址是 4 的倍数，CPU 只需要 **1 次总线时序** 即可读取完毕。
* **非对齐访问**：跨越了两个存储字边界，CPU 需要执行 **2 次总线事务并拼接移位**，在一些低功耗或严格架构（如部分 ARM 内核或严苛硬件模式）下，甚至会直接触发 **`HardFault / Alignment Fault`** 硬件异常！

---

## 2. 默认对齐的三大核心规则

编译器默认遵循以下三条原则：

1. **首地址对齐**：结构体的起始存储地址能够被其最宽的基本类型成员大小整除。
2. **成员自身对齐**：结构体每个成员相对于结构体首地址的偏移量（Offset），必须是该成员自身大小的整数倍。如果不是，编译器会自动在成员间插入**空字节（Padding）**。
3. **整体大小对齐**：结构体的总占用字节数，必须是其**最宽成员大小**的整数倍（以便在结构体数组中依然能自然对齐）。

## 3. 代码实例与内存布局对比

### ❌ 未经排列的结构体（内存浪费）

```c
struct BadSensorData {
    uint8_t  flag;       /* 1 字节, 偏移 0 */
    /* [Padding] 自动填充 3 字节，使下一个 uint32_t 对齐到 4 字节边界 */
    uint32_t timestamp;  /* 4 字节, 偏移 4~7 */
    uint16_t voltage;    /* 2 字节, 偏移 8~9 */
    /* [Padding] 自动补齐 2 字节，满足总大小为 4 的整数倍 */
};

/* sizeof(struct BadSensorData) == 12 字节！(有效数据只有 7 字节，浪费近 42%) */
```

### ✅ 按降序排列（零填充损耗）

调整结构体成员顺序，将大尺寸变量放在前面：

```c
struct GoodSensorData {
    uint32_t timestamp;  /* 4 字节, 偏移 0~3 */
    uint16_t voltage;    /* 2 字节, 偏移 4~5 */
    uint8_t  flag;       /* 1 字节, 偏移 6 */
    /* [Padding] 仅尾部填充 1 字节，使整体大小凑够 4 字节整数倍 */
};

/* sizeof(struct GoodSensorData) == 8 字节！直接节省 33% 内存 */
```

## 4. 通信协议中的 1 字节紧凑对齐

在通信协议（如 [[嵌入式/CAN协议快速入门|CAN 通信报文]]、串口帧）中，我们通常需要关闭对齐，实现紧密打包：

```c
#pragma pack(push, 1)  /* 强制 1 字节紧凑对齐，无任何填充字节 */
typedef struct {
    uint8_t  header;    /* 偏移 0 */
    uint32_t frame_id;  /* 偏移 1 (非 4 字节对齐) */
    uint8_t  payload[8];/* 偏移 5 */
} __attribute__((packed)) TelemetryPacket_t;
#pragma pack(pop)      /* 恢复默认对齐 */
```

> [!WARNING]
> **重大陷阱**：
> 紧凑对齐后的结构体中，`frame_id` 位于奇数地址（偏移 1）。在部分不支持非对齐访问的 MCU 上，**直接用指针引用 `uint32_t *p = &packet.frame_id;` 会引发严重硬件死机！**
> 正确做法是用 `memcpy` 取值，或者交给编译器识别 packed 属性处理。
